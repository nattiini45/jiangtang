# Shipped knowledge about devices lives in data files, and installations keep only identity and their changes

Status: accepted

Jiangtang should know what a projector or a wireless receiver is and what a given model can do,
instead of asking each team to describe it. Teams already define their own fields per device kind,
stored as definition rows with values in a JSON object on each room and device and read by forms,
pages, list columns, filters and the MCP tools. The question was how to add a shipped library of
properties per device kind and a catalog of models with their data sheets, so that later
releases can correct them, the interface speaks both languages, and parts, readings and devices
that report themselves can follow without rebuilding.

## Decision

- **One mechanism for properties.** A library property is an ordinary field definition row
  carrying the library's key. The row gives it identity (the id that values, list columns and
  tools use) and holds what the installation changed: hidden, renamed, moved. Its names, help,
  unit label, option labels, weight and conditions are read from the shipped library file at
  display time in the viewer's language. Type, level and the set of options are copied onto the
  row, because they decide how values are stored, and change only through an explicit step in a
  release.
- **Two levels.** A property belongs to the model or to the device. Model values are stored once
  on the model; a device reads the model's value, falling back to its own value when the model
  has none. A device with a model edits model-level properties on the model only: its form
  shows them read-only with a link, including when the model has no value. A device without
  a model edits them itself.
- **A catalog of models as data.** Models with their data-sheet values, ports and manufacturer
  pages ship as files in the repository. An existing model with the same manufacturer and name is linked to its catalog record by
  the deploy itself and when picked. Linking fills only what is empty and can be undone. A later release corrects a value only where the installation
  still holds what the catalog last wrote.
- **Arriving complete.** On deploy and on installing a kind, the application creates the rows for
  every library property of every installed kind. Nobody configures a basic thing.
- **Readings and relations are not field values.** A reported or observed value is stored as a
  dated reading with its source, and a link to another record as a relation row. Neither is
  stored as a plain field in the meantime. A part is a device kind; its model, its stock and a
  fitted unit are separate records joined by the model.
- **Additive only.** Schema changes add columns and tables; old fixed columns are copied into
  library properties by the application and kept until a later release.

## Consequences

- A corrected name or label reaches every installation without a data migration, unless the
  installation renamed the property.
- Every reader of field definitions goes through one resolving function; reading definitions
  straight from the table bypasses the library and shows stale names.
- Changing a property's type or level in the library needs a data move shipped with that release;
  the reconcile refuses it otherwise.
- The library and catalog files grow the repository by a few hundred kilobytes per release and
  are generated by scripts kept beside them; they hold facts and source addresses only.
- Limits on a team's own fields do not count library properties.

- A new enum value ships one release before the first row uses it, so rollback code can skip
  values it cannot render.

This release builds projector properties, their reconcile and resolver, and model values; the
model catalog, picking and linking follow in the next release.
